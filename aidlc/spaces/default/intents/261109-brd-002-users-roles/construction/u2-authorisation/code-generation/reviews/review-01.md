| R-01 | Major | services/identity/application/src/authorisation/decision.rs > `owned_by_caller` and the `OperationClass::Collection` arm | A job caller is not bound to any owner. `owned_by_caller` returns `true` for a `CallerIdentity::System` whenever a row owner is present, whatever that owner is, and a system collection returns `Decision::allow(None)` when no owner id is supplied. W4 and the decision table in `functional-spec.md` require a job to act only for "the iterated owner" (row: allow for that owner, deny a foreign row; collection: allow plus owner filter). As built, the decision cannot detect a job writing owner B's row under owner A, and can hand a job a collection allow with no filter at all. | Give the system caller the owner it is iterating (a required owner on `CallerIdentity::System` or an extra decision argument), deny a row whose owner differs and a collection with no stated owner, and add tests for both. | New |
| R-02 | Major | services/identity/http/src/authorisation.rs > `ROLE_CHANGE_SERVICE` and `require_internal_caller` | The admin role-change endpoint accepts only a service token that resolves to `gateway`, but nothing wires the gateway to it. The gateway's route table (`services/gateway/domain/src/route.rs`) has no `/internal/admin/role` route, the gateway stack block has no identity service-token secret or `x-service-token` client code, and the infrastructure specification's provisioning table plus the plan's caller-wiring step name only `account-api` and `portfolio`. BR2.10 therefore has no reachable entry point in production: every caller gets 401 (unknown service) or 403 (not the gateway). | Wire the gateway caller end to end (route, `x-service-token`, `identity_service_tokens` entry), or record the admin caller as deferred to a named unit and reconcile the C4 wording ("the calling service is not the gateway") with what is actually provisioned. | New |
| R-03 | Major | services/identity/infrastructure/src/authorisation/role_writer.rs > `set_role` | The provider write sends only `{"app_metadata": {"role": ...}}`. Identity reads `app_metadata.has_exchange_credentials` from the token to derive `next_step()` and require MFA (`services/identity/domain/src/claims.rs`; project rule "MFA for users who have exchange credentials"). If Supabase Auth's admin update treats the supplied `app_metadata` as the user's new app-metadata object rather than merging it, every role change drops all other provider-managed keys and silently removes the MFA requirement for that user. Nothing reads the current metadata before writing, and no test pins the behaviour. | Read the target user's current `app_metadata` and merge the role into it before the write (or prove the provider merges) and cover it with a test against the local Supabase Auth, so a role change cannot erase `has_exchange_credentials`. | New |
| R-04 | Major | services/identity/tests/authorisation_application.rs > role-change cases; services/identity/infrastructure/src/authorisation/{audit,role_writer}.rs | The two adapter writes that carry BR2.10, BR2.11 and BR2.12 are only ever exercised through fakes. `AuthorisationAuditSink` (fail-closed denial write, the `eyJ`/`0x`+40-hex redaction backstop) and `SupabaseRoleWriter` (the provider payload) have no test at all, so a wrong payload, an ignored redaction, or a 4xx misread as success would pass the suite. | Add adapter tests against a stub HTTP server for each: the success payload, a 5xx/4xx answer, and a token-shaped or wallet-shaped value being refused by the audit sink. | New |
| R-05 | Minor | services/identity/http/src/authorisation.rs > `may_ask` | The allowlist is per class, not per operation: `account-api` and `portfolio` may ask for any `admin:*` (Administrative) and for `guard:confirm`, although C4 says "each service may ask only for the operations its table row names" and their stated purpose is BR2.13 linkage. A service-token compromise therefore widens the operations those two services can put to the decision. | Restrict each service to the concrete operations it needs (owner-scoped and collection for BR2.13) and refuse administrative and confirmation names unless a design names them. | New |
| R-06 | Minor | aidlc/spaces/default/intents/261109-brd-002-users-roles/inception/contract-design/contract-summary.md > C4 "Consumers" | The contract lists U3, U7, U9 and U10 as C4 consumers, but `IDENTITY_AUTHORIZE_SERVICES` and `may_ask` admit only `account-api`, `portfolio` and `identity-smoke`. A declared consumer would be refused with 403 if it followed the contract. | Reconcile the consumer list with the allowlist (and with the functional spec's statement that the TypeScript surfaces never call C4) so a declared consumer is not refused at runtime. | New |
| R-07 | Minor | services/identity/application/src/authorisation/role_change.rs > intent/outcome audit failure | An audit refusal that arrives as `RepositoryError::Validation` — the sink's own redaction refusal — is mapped through `AppError::from_repository` to a 422 naming field `subject`, while the C4 contract promises 503 when the intent or outcome entry cannot be recorded. | Map every audit-write failure on the role-change path to the unavailable (503) outcome, independent of the repository error variant. | New |

### Summary

The decision core is faithful to W1 — declared, status, support, administrative-by-role, collection filter, ownership — and the role-change ordering is correct and tested. The blocking concerns are integration and enforcement: a job caller is never bound to a stated owner, the admin role change has no reachable caller, the provider role write may erase the `has_exchange_credentials` claim that drives MFA, and the two adapter writes carrying BR2.10–BR2.12 have no test behind them.
