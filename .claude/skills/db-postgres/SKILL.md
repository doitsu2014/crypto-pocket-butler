# PostgreSQL Integration

Apply this skill whenever a stage touches a PostgreSQL database: data-model and
schema design, migrations, queries, transactions, performance, or tests.

## When this skill applies

- Inception: choosing PostgreSQL, designing the schema, or defining the
  contract.
- Construction: writing queries, repositories, migrations, or seed data.
- Construction: containerised test databases, CI migration runs, fixtures.
- Operation: index and query-plan review, slow-query triage, bloat.

## Configuration and secrets

- Connect with a single URL: `postgres://user:pass@host:5432/db?sslmode=require`.
- Read credentials from environment/secret manager only. Never commit them.
- Always set `sslmode` (`require` or `verify-full` for managed services).
- Set an explicit `application_name` so queries are attributable in `pg_stat_activity`.
- Set `search_path` explicitly if you rely on non-`public` schemas.
- Use a least-privilege role per service; grant only the DML/DDL it needs.

## Drivers and ORMs (pick one per codebase and record it)

| Ecosystem | Driver | Common ORM/query layer |
| --- | --- | --- |
| Node/TypeScript | `pg` (node-postgres) | Prisma, Drizzle, TypeORM, Kysely |
| Python | `psycopg` (3) / `asyncpg` | SQLAlchemy, Django ORM, Piccolo |
| Java/Kotlin | JDBC (`org.postgresql`) | Hibernate/JPA, jOOQ, MyBatis |
| Go | `pgx`, `database/sql` | sqlc, GORM, Ent |
| .NET | Npgsql | EF Core, Dapper |

Record the driver and version in `construction/nfr-requirements`, and the
pooling strategy in `construction/nfr-design`.

## Schema and data modelling

- Prefer `GENERATED ALWAYS AS IDENTITY` (or `GENERATED BY DEFAULT`) over `serial`.
- Use `uuid` with `gen_random_uuid()` (`pgcrypto`) only when IDs must be
  generated client-side; otherwise `bigint` identity is cheaper to index.
- Use `timestamptz` (never `timestamp` without time zone) for instants.
- Normalise first; denormalise deliberately with a recorded reason.
- Model enums as `text` + `CHECK` or a lookup table; native `enum` is painful
  to evolve.
- Use `JSONB` for genuinely schemaless attributes, not as a substitute for
  columns you query and constrain.
- Add `NOT NULL`, `CHECK`, and foreign keys by default. Constraints are the
  cheapest correctness you will ever buy.
- Name things consistently (`snake_case`, singular table names or plural —
  choose one and enforce it).

## Migrations

Choose one tool and make every schema change a reviewed, forward-only
migration:

- Prisma Migrate, Drizzle Kit, Kysely migrations
- Flyway, Liquibase (language-agnostic)
- Alembic (Python), goose/dbmate/golang-migrate (Go), EF Core Migrations (.NET)

Rules:
- Migrations are immutable once merged. Fix forward with a new migration.
- Separate schema changes from data backfills.
- Take an explicit lock (`LOCK TABLE ... NOWAIT` or a short `lock_timeout`) and
  set `statement_timeout` so DDL cannot block the cluster indefinitely.
- Adding a column is cheap; adding a `NOT NULL`/default on a large table,
  changing a type, or adding an index is not. Use `CREATE INDEX CONCURRENTLY`
  outside a transaction and expect it to fail-fast if it cannot complete.
- For destructive changes: expand → migrate → contract across releases.

## Query patterns and performance

- Index for the access pattern, not the schema. Composite index column order
  matters (equality columns first, then range/sort).
- Use partial indexes for hot subsets and expression indexes for computed
  lookups.
- Read plans with `EXPLAIN (ANALYZE, BUFFERS)`; look for seq scans on large
  tables, row-estimate blowups, and nested loops over many rows.
- Watch for N+1 queries from ORMs; use joins, `IN` batches, or dataloaders.
- Prefer keyset (cursor) pagination over `OFFSET` for large tables.
- Use CTEs and window functions instead of pulling rows into the application.
- `VACUUM`/autovacuum and bloat matter: a hot table with dead tuples is a
  performance incident waiting to happen.

## Transactions and concurrency

- Default isolation is `READ COMMITTED`. Use `REPEATABLE READ` or
  `SERIALIZABLE` only with a retry-on-serialization-failure strategy.
- Keep transactions short; never hold one open across a network or user wait.
- Use `SELECT ... FOR UPDATE` (or `FOR NO KEY UPDATE`) deliberately.
- Use advisory locks (`pg_advisory_xact_lock`) for application-level mutexes.
- `LISTEN`/`NOTIFY` for lightweight pub/sub; do not treat it as durable.

## Connection pooling

- A pool belongs to the process; size it from the database's connection limit,
  not from request concurrency. Start near `2 * CPU cores` per instance.
- Behind PgBouncer in transaction mode, disable server-side prepared
  statements or enable protocol-level support — otherwise you get subtle
  failures.
- Always set connect, statement, and idle-in-transaction timeouts.

## Security

- Parameterise every query. Never string-concatenate SQL.
- Use row-level security (RLS) for multi-tenant isolation where appropriate,
  and set the tenant context per transaction.
- Encrypt sensitive columns (`pgcrypto`) or, better, encrypt in the application
  with keys outside the database.
- Audit who can `COPY`, `pg_read_server_files`, and `SUPERUSER`.
- Never log full connection strings or row values that contain PII.

## Testing

- Use Testcontainers (`postgres`) or an ephemeral service for integration
  tests; do not test against a shared developer database.
- Run migrations as part of test setup so tests exercise the real schema.
- Reset state between tests (truncate or transaction rollback); avoid
  order-dependent fixtures.
- Assert on constraints and errors, not just happy paths.
- Seed minimal, deterministic data; never copy production data.

## Observability and operations

- Enable `pg_stat_statements`; alert on top queries by total time, not just
  mean.
- Track connections, cache hit ratio, replication lag, deadlocks, and
  transaction wraparound.
- Define backups and test restores; a backup you have never restored is a
  hypothesis.
- For rollback, prefer reversible migrations or a paired down-migration; for
  destructive changes, rely on the expand/contract sequence.

## Common pitfalls

- Assuming `READ COMMITTED` prevents lost updates (it does not).
- Long-running `ALTER TABLE`/`CREATE INDEX` taking locks on a live table.
- Storing timestamps without time zone.
- Treating `NULL` as `''` or `0` in unique constraints and predicates.
- Forgetting `CONCURRENTLY` and wrapping it in a transaction.
