| R-01 | Major | services/identity/application/src/export.rs > ExportWorker::run_once, and services/identity/infrastructure/src/repositories/exports.rs > update | The worker claims a 60-second lease but never renews it: the claim-time `lease_until` is written back unchanged on every progress update, and the sweep runs every 60 seconds, so a live worker whose three contributor calls plus storage upload take longer than 60 seconds is treated as dead. The next pass claims the same request and re-calls every contributor from the start (the loop does not skip contributions already recorded as succeeded). Both workers then write `progress` last-writer-wins, so progress can move backwards, and a completed deletion can be overwritten by the other worker's stale `failed` write (the deletion `update` writes status unconditionally). This contradicts NFR20.3's "no duplicate execution" and the code summary's claim that a claim prevents double execution. | Renew the lease on each step, or verify lease ownership in `update` and refuse a stale writer, and skip already-succeeded contributions on a re-claim. Add a test where a live worker's pass exceeds the lease. | New |
| R-02 | Major | services/identity/infrastructure/src/auth.rs > validate_with_keys, and services/identity/application/src/principal.rs > provision | The verified-to-active transition depends on a top-level `email_confirmed` or `email_confirmed_at` JWT claim. A standard Supabase access token carries `email` and `user_metadata.email_verified`, not those top-level claims, and nothing in this unit configures a custom access-token hook that would add them. Every identity test injects a hand-built `VerifiedClaims` through `FakeTokenValidator`, so the real JWT-to-principal mapping is never exercised: if the claim is absent in production, every user stays `pending` permanently and the suite still passes. This is the functional-design question R-02 carried into code. | Pin the claim source (a documented custom access-token hook, or read `user_metadata.email_verified`), and add a test that decodes a realistic Supabase token through `JwksValidator` into a principal. | New |
| R-03 | Major | services/identity/infrastructure/src/repositories/users.rs > insert and reveal_auth_subject, and services/identity/tests/repositories.rs | The repositories call `identity.protect`, `identity.unprotect`, `identity.create_shredding_key`, and `identity.destroy_shredding_key` with a hard-coded schema name, but `test_pool()` runs the migration into a disposable `test_identity_<uuid>` schema, where those functions exist only as `<test schema>.protect` and similar. ### Summary

The service is well structured and the runnable suite, formatting, lint, and boundary gates all pass, but the worker's non-renewed lease permits duplicate execution and stale writes, activation rests on a JWT claim nothing verifies or tests, and the database adapter suite cannot run against the disposable schema it creates. Those three gaps plus the liveness-only Swarm health check are what a reviewer should weigh before this is approved.
